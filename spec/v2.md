# AgentWharf Hub Protocol v2

## Status

This is the current protocol specification. It inherits v1 only where this
document does not version a rule differently. The generic Hub remains
host-neutral: platform extensions are opaque types and payloads.

## Negotiation

- A peer that negotiates `protocol_version: 2` receives v2 rules only.
- A peer that negotiates v1 receives only frozen legacy rules from `v1.md`.
- One logical publisher warning maps to exactly one event type per connection.
  Dual emission is forbidden.

## Historical Pagination

`history.page` is a v2-only, capability-gated explicit client read. It is not
reconnect replay, live delivery, or a request to replay an entire Task. The Hub
accepts and returns one authorized `session_id`; deployments join Task/Run
references outside this protocol, and a multi-Run Task pages each referenced
Session separately.

Only a v2 `hello.ack` that includes
`capabilities.history_page: { "max_limit": 100 }` permits the frame. A v1
acknowledgement omits the capability and a v1 `history.page` frame receives
`error(code=history_unsupported)` without changing live subscription, replay
cursor, or durable state.

```json
{
  "frame": "hello.ack",
  "protocol_version": 2,
  "sessions": [],
  "capabilities": {
    "history_page": { "max_limit": 100 },
    "attention_summary": { "max_sessions": 64 },
    "settings": {
      "schema_version": 1,
      "max_pending_changes": 1,
      "provider_response_timeout_seconds": 30
    },
    "run_control": {
      "schema_version": 1,
      "max_pending": 1,
      "completion_timeout_seconds": 30
    }
  }
}
```

```json
{
  "frame": "history.page",
  "request_id": "hist_01H8X",
  "session_id": "ses_01H8X",
  "before_seq": 58,
  "limit": 100
}
```

Rules:

1. `before_seq` is an exclusive cursor. When omitted, the Hub captures the
   current latest durable sequence in the read snapshot and returns the newest
   page. When supplied, it returns only events with `seq < before_seq`.
2. `limit` is required and MUST be in `1..100`. A response can contain fewer
   events only because fewer retained events satisfy the cursor; a Hub MUST NOT
   scan or replay unbounded history to fill a page.
3. Only a client with existing authorized `session:<id>:control` or
   `session:<id>:view` read authority may page that Session. Adapter tokens,
   `api:*`, and unauthorized group membership do not grant history paging.
4. The client MUST use `next_before_seq` unchanged for the next older page. It
   MUST NOT substitute `last_seq`, a timestamp, Task/Run identifiers, or local
   cache state.

The response contains the request and Session IDs, durable `events`,
`latest_seq`, `next_before_seq`, and `retention_state`:

```json
{
  "frame": "history.page",
  "request_id": "hist_01H8X",
  "session_id": "ses_01H8X",
  "events": [
    { "frame": "event", "type": "session.message", "seq": 52, "time": 1764937200123, "payload": {} },
    { "frame": "event", "type": "session.tool_call", "seq": 53, "time": 1764937201123, "payload": {} }
  ],
  "latest_seq": 57,
  "next_before_seq": 52,
  "retention_state": "complete"
}
```

Rules:

1. `events` contains durable event envelopes only, in strictly ascending `seq`
   order. Ephemeral events, heartbeats, cached rows, and synthetic sequence
   numbers never appear.
2. A non-null `next_before_seq` equals the smallest `seq` in this page and
   means earlier retained events exist. `null` means none remain. A client can
   call history complete only when `next_before_seq` is `null` and
   `retention_state` is `complete`.
3. `retention_state` is `complete` or `retention_gap`. `retention_gap` means
   at least one earlier durable range was pruned. It MUST be returned for both
   empty and non-empty pages and MUST render as an explicit gap, never an empty
   successful history.
4. A deleted, unauthorized, or temporarily unavailable Session returns
   `error(code=history_unavailable)` without an empty successful page.

The v2 EventStore interface adds `History` without changing forward replay:

```go
type HistoryPage struct {
    Events         []Event
    LatestSeq      int64
    NextBeforeSeq  *int64 // nil: no earlier retained event
    RetentionState string // "complete" | "retention_gap"
}

type EventStore interface {
    Append(ctx context.Context, sessionID string, evs []PendingEvent) (firstSeq int64, err error)
    Replay(ctx context.Context, sessionID string, afterSeq int64, fn func(Event) error) error
    History(ctx context.Context, sessionID string, beforeSeq *int64, limit int) (HistoryPage, error)
    LatestSeq(ctx context.Context, sessionID string) (int64, error)
}
```

## Attention Summary Subscription

`attention.subscribe` is a v2-only, capability-gated read of a bounded set of
provider-neutral Session summaries. It is not a Task/Run query, transcript
subscription, event replay, historical pagination, or adapter management path.
The Hub accepts Session IDs only and never reads deployment business tables.

Only a v2 `hello.ack` with
`capabilities.attention_summary: { "max_sessions": 64 }` permits the frames.
A v1 acknowledgement omits the capability and v1 frames receive
`error(code=attention_unsupported)`. An attention-scoped client uses a separate
connection and MUST NOT request ordinary `subscriptions` or `last_seq` replay.
Conversely, `control` and `view` do not imply attention access.

```json
{
  "frame": "attention.subscribe",
  "request_id": "attn_01H8X"
}
```

Rules:

1. `attention:<id>` is a short-lived, non-upgradeable client scope. Auth maps
   it to an opaque grant containing a canonical issuer-ordered Session
   allowlist, cap, and expiry. The Hub takes the first
   `min(grant.max_sessions, 64)` entries. Grant order is the sole
   inclusion/eviction tie-break: the Hub neither reads Task priority nor sorts
   or independently selects members. A duplicate, invalid, or empty allowlist,
   or a cap outside `1..64`, fails closed as detail-free
   `attention_unavailable`.
   `group:*`, `api:*`, `session:*:adapter`, `view`, and `control` cannot
   substitute for the grant.
2. A connection has at most one attention subscription. Every subscribe frame
   atomically rebuilds membership from the current grant's ordered prefix: the
   Hub swaps only after its new snapshot is readable and then emits it; failure
   clears membership and emits no partial result. Authorization change, expiry,
   identity change, or close removes membership. Reconnect starts empty and
   needs a current-identity subscribe frame and snapshot. The Hub uses shared
   per-Session fanout and MUST revalidate grant identity, expiry, revocation,
   and exact allowlist at membership replacement, snapshot read, and
   immediately before every update fanout. On failure it clears membership
   before sending, so no queued frame can disclose a summary.
3. The Hub uses shared per-Session
   fanout and MUST NOT allocate an unbounded goroutine, timer, queue, or scan
   per member or historical subscription.

The Hub returns the initial snapshot and subsequent changes as:

```json
{
  "frame": "attention.summary",
  "request_id": "attn_01H8X",
  "kind": "snapshot",
  "subscription_state": "complete",
  "summaries": [
    {
      "session_id": "ses_01H8X",
      "latest_seq": 57,
      "state": "waiting_permission",
      "permission": { "id": "pr_01H90", "status": "pending" },
      "terminal_outcome": null,
      "latest_change_seq": 55,
      "blocker": {
        "kind": "queued",
        "reason": "capacity",
        "expires_at": 1764937800000,
        "blocking_session_id": "ses_01H8Z"
      },
      "summary_version": 12,
      "summary_state": "complete"
    }
  ]
}
```

Rules:

1. `kind` is `snapshot` or `update`. A snapshot is emitted only after an
   authorized membership replacement or reconnect. An update contains only
   current members with any changed summary field. Event-backed field changes
   MUST emit an update even if `summary_version` did not change;
   `summary_version` identifies ledger-only evidence. Within a frame, summaries
   are sorted by `session_id`; their order never establishes cross-Session
   event or work order.
2. A summary contains only its Session ID, Hub-issued `latest_seq`,
   provider-neutral `state`, optional unresolved `permission={id,status}`,
   optional `terminal_outcome`,
   `latest_change_seq`, optional `blocker`, and monotonic per-Session
   `summary_version`. `permission.id` is an opaque existing permission request
   ID and `permission.status` is only `pending`; after resolution permission is
   null and no action, risk, detail, or provider object is exposed.
   `blocker.kind` is `queued`, `reauthorization_required`,
   `new_run_required`, or `outcome_unknown`; only `queued` can carry `reason`,
   `expires_at`, and `blocking_session_id`. The latter is sent only when its
   blocking Session is also in the current, just-revalidated attention
   membership; otherwise it is silently omitted and neither an error nor an
   empty sentinel distinguishes an unauthorized or missing relationship. Only
   `outcome_unknown` can carry a bounded `operation`. Summaries MUST NOT contain Task/Run IDs,
   transcript text, messages, tool output, file/diff data, credentials,
   provider objects, browser cache values, or synthetic sequence values.
3. `latest_seq` and `summary_version` are independent version domains. Clients
   use `latest_seq` only for durable-event evidence and `summary_version` only
   for ledger-only blocker/attachment/delivery evidence. Neither substitutes
   for the other, confirms transcript read, creates a global cursor, or changes
   replay/history/live-event behavior.
4. `subscription_state` and `summary_state` are `complete` or `incomplete`.
   A missing, stale, corrupt, incompatible, or unbuilt projection MUST be
   explicit `incomplete`, never a fabricated no-attention result. Only a
   snapshot with any current member `incomplete` MUST itself be `incomplete`.
   Only a
   separate checkpointed maintenance/backfill process may build summaries, in
   batches of at most 256 Sessions; subscription requests MUST NOT scan or
   rebuild full history.

The EventStore owns the durable projection. Event append and changes to
`latest_seq`, state, permission, terminal outcome, `latest_change_seq`, and
the original Store-clock `last_durable_event_at` commit in the same transaction.
An accepted client-command ledger mutation commits its original Store-clock
`last_client_command_at` and the new `summary_version` in its own transaction;
queued, reauthorization, new-run-required, and outcome-unknown ledger changes
likewise atomically commit their blocker and version. Ledger writes never
allocate, reuse, or replace durable event `seq`.

Ephemeral events, adapter heartbeats, supervisor liveness, dispatcher or
callback receipts, and retry cadence MUST NOT advance either timestamp, seq,
summary version, or blocker. After rollback, restart, concurrent writes, or
retention, the Store exposes one committed projection or `incomplete`; it never
fabricates idle or no-attention truth.

An attention scope can receive only the summary frames above. It cannot
subscribe to durable or ephemeral events, replay or page history, attach,
reauthorize or rotate an adapter, obtain credentials, send commands, answer
permissions, or mutate Session/summary state. Such frames fail their existing
authorization checks without changing a live subscription, ledger, or Store.

The v2 interfaces add the following contracts without changing the v1
EventStore interface:

```go
type AttentionBlocker struct {
    Kind              string // queued | reauthorization_required | new_run_required | outcome_unknown
    Reason            *string
    ExpiresAt         *time.Time
    BlockingSessionID *string
    Operation         *string
}

type AttentionPermission struct {
    ID     string // opaque permission request ID
    Status string // pending
}

type SessionAttentionSummary struct {
    SessionID           string
    LatestSeq           int64
    State               string
    Permission          *AttentionPermission
    TerminalOutcome     *string
    LatestChangeSeq     *int64
    Blocker             *AttentionBlocker
    SummaryVersion      int64
    LastDurableEventAt  *time.Time
    LastClientCommandAt *time.Time
    StateOfProjection   string // complete | incomplete
}

type AttentionGrant struct {
    SessionIDs  []string // Auth-supplied canonical order; Hub consumes its bounded prefix
    MaxSessions int
    ExpiresAt   time.Time
}

type AttentionSummaryStore interface {
    AttentionSnapshot(ctx context.Context, sessionIDs []string) ([]SessionAttentionSummary, error)
}

type AttentionAuthorizer interface {
    AuthorizeAttention(ctx context.Context, p Principal) (AttentionGrant, error)
}
```

## Managed Launcher Handoff

Deployments can use an outer launcher to obtain an Adapter credential through
their own control-plane flow. That flow is outside AgentWharf: the generic Hub
and Adapter core know neither claim codes, machines, users, organizations,
Tasks/Runs, nor control-plane endpoints. The only permitted handoff is:

```go
type AdapterLaunch struct {
    SessionID       string
    HubWSURL        string
    AdapterToken    SessionCredential // opaque, non-marshallable
    ExpiresAt       time.Time
}
```

Rules:

1. A launcher validates a complete unexpired handoff before it starts an
   Adapter. The Adapter uses only the exact `SessionID`, `HubWSURL`, and
   Session-scoped credential in its normal adapter hello. It never receives or
   logs the external exchange inputs or a broader credential.
2. `AdapterToken` MUST NOT travel in argv, environment, standard streams,
   process title, persistent files, local databases, crash dumps, or a provider
   child-readable location. An outer-process handoff uses a protected one-read
   descriptor or an equivalent mechanism that is closed after Adapter receipt.
   If that cannot be guaranteed, the launcher fails closed.
3. The launch lease ends at `ExpiresAt`. While the parent launcher remains
   alive and the credential is unexpired, it can make at most two total Adapter
   spawn attempts, both with the same handoff. A first non-auth crash or
   connection failure consumes the only restart and permits the second spawn.
   An accepted exact-session adapter hello completes launch; later reconnect
   follows normal Adapter semantics only until expiry or revocation. An
   explicit auth rejection, parent loss, expiry, or the second failed attempt
   destroys the handoff and cannot trigger an automatic credential exchange,
   token rotation, or scope change.
4. The launcher reports an explicit external reauthorization/reclaim-required
   state after lease loss. It does not persist or replay a consumed exchange
   input, infer whether an external claim was consumed, or silently substitute
   a new session/credential.

No new Hub frame or EventStore record is introduced by this handoff. Provider
startup, secrets, and recovery remain Adapter concerns; the Hub remains
Session-first and validates only its existing adapter authorization.

## Bootstrap Assignment And Target Worker Admission

This v2 contract permits one already-connected Session to assign a bounded
target Session to a platform-neutral supervisor. It names only opaque Session
identities; it has no Task, Run, VM, tenant, billing, control-plane URL, or
provider-object field. A `bootstrap` is the currently eligible Session that
receives an assignment. A `target` is a different Session that may receive one
assignment. These are authorization roles for one attempt, not token scopes,
Hub groups, or durable business concepts.

Every adapter connection remains one Session and one `session:<id>:adapter`
credential. There is no group credential. A target credential is created only
after its attach commits, belongs only to the target, and is never delivered to
the bootstrap, Client, Provider process, outbox, transcript, analytics, audit
metadata, or log.

### Grant And Fresh Target Admission

`session.attach` requires both an authenticated
`session:<target>:control` Client and an opaque signed attach grant. The grant
has a deployment-injected fixed attach audience which Hub compares exactly but
never interprets, one `jti`, `iat`, `exp`, bootstrap Session ID, target Session
ID, stable opaque attach ID, provider identifier, and an opaque Store-allocated
monotonic `grant_fence`. Its maximum lifetime is five minutes; verification
permits at most 30 seconds of clock skew. The grant is neither an Adapter
credential nor a general Client, history, attention, API, or control credential.
The deployment MUST mint and validate an opaque delivery deadline such that
its 30-second post-expiry delivery grace cannot outlive the issuer's own
persisted authorization lease. Hub consumes only that grant-bound deadline; it
does not read or depend on a Control Plane field or table.

A fresh target without durable Store truth may connect only with a short-lived
`attach_only` Client principal bound to that exact target Session, provider,
and expiry. Before durable attach commit it may submit only the exact
`session.attach` and its status query. It MUST reject send, history, settings,
run-control, permission, credential rotation, and every other mutation. Commit
upgrades authority from durable Store truth; it never mutates the token. An
ordinary control token alone cannot attach, and the grant alone cannot send
content or control either Session.
Only exact `session:<target>:control` satisfies the Client half: `api:*`,
group, view, attention, Adapter, and wildcard/broader scopes are rejected. Hub
consumes the raw grant only at Client-to-Hub ingress; it and `attach_only` never
enter an assignment, join, Adapter frame, sandbox, Provider, Store/outbox, or log.

The Hub accepts an attempt only from the current, normal-hello bootstrap
WebSocket. Its Store connection record supplies the bootstrap's active
credential generation, connection epoch, and monotonic `accepted_fence`.
Admission requires `grant_fence > accepted_fence` and binds the attempt to
`(bootstrap_session_id, active_credential_generation, connection_epoch,
accepted_fence)`. A normal hello or activation advances accepted_fence; a grant
minted before reconnect or rotation is stale without relying on timestamp
precision. Historical handshakes, replayed events, caches, target Sessions,
ended Sessions, and Client claims cannot substitute for this live authority.

### Bounded Capability And Request Proof

A live Adapter advertises provider/capability data only in its normal v2 hello.
At attach, Hub consumes it only from the grant-bound live bootstrap connection.
The Hub accepts at most 64 KiB of decoded capability and attach-request metadata,
at most 64 capabilities, and identifiers/strings no longer than 256 bytes. It
applies the WebSocket read limit before decoding, rejects unknown, duplicate,
ambiguous, oversized, or non-canonical fields before persistence, and never
trusts a Console cache as capability evidence.

#### Adapter Normal-Hello Capability Schema

This is a field extension of the existing `hello` frame, not a new frame type.
An authenticated v2 Adapter normal hello may omit `capabilities`. Omission is
valid and means that it advertises no v2 Adapter capability. The only currently
accepted non-empty object is the following exact decoded object:

```json
{
  "frame": "hello",
  "protocol_version": 2,
  "role": "adapter",
  "token": "<session-bound adapter token>",
  "session_id": "ses_01H8X",
  "provider": "claude-code",
  "resume": true,
  "capabilities": {
    "multi_worker_process_ownership": true
  }
}
```

The v2 Adapter normal hello has exactly the inherited Adapter members `frame`,
`protocol_version`, `role`, `token`, `session_id`, `provider`, and `resume`,
plus optional `capabilities`; an unknown top-level member is rejected. The
`capabilities` value MUST be an object with exactly one member named
`multi_worker_process_ownership`, whose value is the JSON literal `true`.
Decoders MUST preserve object-member presence until validation and reject
duplicate members at every level, including duplicate top-level `capabilities`
or nested `multi_worker_process_ownership`; decoding into a lossy map is not
sufficient. `false`, `null`, a non-object, an empty object, an unknown key, a
missing key, a non-boolean value, or a non-canonical/ambiguous representation
MUST NOT be normalized to omission or accepted as an affirmative capability.

The Hub validates this object only after authenticating the exact
`session:<id>:adapter` principal and resolving the normal hello against its
current connection record. Bootstrap is an attach-attempt role supplied only by
the later grant, so a well-formed object on another current Adapter connection
is not a hello-time error and grants no behavior. A stale/revoked/expired/
prior-generation/old-epoch connection is rejected before it can become live.
At `session.attach`, the Hub uses the grant-bound bootstrap Session ID to
require an accepted object on that exact live connection, bound to
`(bootstrap_session_id, active_credential_generation, connection_epoch,
accepted_fence)`. An object advertised by a target or any other non-bootstrap
connection has no assignment effect. A missing, rejected, or subsequently
fenced object denies the assignment, so a historical hello, cache, or value
copied from a Provider can never authorize an attachment.

The Client sends only bounded canonical inputs. Hub alone computes the
HMAC-SHA256 fingerprint using domain
`agentwharf.attach-request.v1` over a versioned length-delimited canonical
encoding of attach/bootstrap/target/provider IDs, capability fingerprint,
command ID, digest of canonical first-command bytes, and ordered attachment
reference metadata/digests. A Client digest, key version, or HMAC is never an
authorization or idempotency proof. The Hub stores only its computed key version
and digest. Raw keys, commands, grants, and credentials are never stored. Retired
verification keys remain usable until dependent attempts expire; missing key
material fails closed. Same-attempt retry requires identical JTI and
fingerprint; changed identity or fingerprint rejects and audits without
mutating current state.

### Atomic Commit And Credential Delivery

The Hub composes one Store transaction for immutable admission result, explicit
attachment/delivery state, target credential lineage, durable initial-user-message
reference/outbox, and a `join_pending` summary blocker. The transaction CAS
rechecks grant/grace expiry, bootstrap active generation/epoch/accepted fence,
nonterminal state, and target eligibility. It records only opaque IDs,
attempt JTI hash, fingerprint digest/key version, expiry, outcome, generation,
and reference metadata; it stores neither command body nor bearer. A failed
transaction delivers no credential and leaves no partial attachment, delivery,
lineage, outbox, or blocker.

`SessionCredentialIssuer` prepares target bearer material without a persistent
side effect. The bearer is discarded if the Store transaction fails. Only after
commit may the Hub deliver it on the pending target join socket; that socket is
credential-delivery-only and cannot emit target events or ledger operations.
The target then opens its normal Session-scoped Adapter socket and must complete
normal hello before any queued/start work. A one-time join nonce binds the
pending socket to target, attempt, bootstrap active generation, epoch, accepted
fence, and strict expiry; any change invalidates it before delivery. It is not
reusable after commit, expiry, socket close, or fencing.

Each side effect checks the live tuple
`(connection_epoch, active_credential_generation, !revoked, !expired,
nonterminal)` immediately before it acts. Failure closes the current socket,
fences queued frames, drops unstarted work, and permits only fail-closed
cleanup. Target and bootstrap lineages are independent. Rotation prepares a
pending bearer, delivers it only on the same-Session unfenced socket, receives
a possession acknowledgement carrying accepted epoch, atomically activates it,
and returns an activation receipt. Delivery/receipt loss retries by stable
rotation ID; pending never acts. Prior recovery may only query/reissue the
already-active generation and cannot normal-hello, advance fence/epoch, emit
events, send commands, or start a Provider. Revocation is zero grace.

### Delivery And Workspace Safety

The Hub derives immutable workspace lease identity; no Client, Adapter, or
Provider may choose it. The target reserves capacity and writer lease before
it atomically records `start_received`. A queued target has a bounded reason
and expiry, cannot start a Provider, and cannot propose `start_received`.
There are three non-interchangeable receipts: routing `command.ack` is keyed by
`cmd_id`; a ledger operation uses `operation_id` and returns monotonic ledger
version; a durable event proposal uses `proposal_id` and returns authoritative
EventStore sequence. All validate the live tuple; routing/ledger never proves
Provider outcome.

Required order is: attach commit; post-commit credential delivery; target
normal hello; optional queued state; writer lease; durable `start_received`
acknowledgement; Provider spawn; durable `session.state=starting`
acknowledgement; first-command received acknowledgement; Provider command
execution. If `start_received` is absent, retry/reauthorization is safe because
the Worker cannot start. If it exists without a trustworthy outcome, delivery
becomes bounded `outcome_unknown` for `start`; Hub never auto-replays it. A
durable first-command receipt without trustworthy Provider outcome likewise
becomes `outcome_unknown` for `command` and is never auto-replayed.

An exact committed retry returns its original non-secret result without
redelivering an old credential. A fresh attempt may recreate a target only when
durable truth is `reauthorization_required` and no healthy target Worker exists.
A healthy target returns current truth without credential rotation, epoch
advance, or fencing. Bootstrap termination blocks new assignment but does not
promote a target or silently rebind an old attachment.

### Provider Process Ownership Gate

Multi-Worker capability is a runtime-local Adapter Group property, not a Hub
role, credential scope, Client claim, Store field, or Provider assertion. The
only accepted affirmative advertisement is the exact normal-v2-hello object
defined above. GroupSupervisor computes it from its local enablement evidence;
Provider output, Client input, cache, or historical hello cannot set or upgrade
it. At attach, only the grant-bound live bootstrap connection's object is
consumed; a target or other Adapter's object has no assignment effect. Missing,
false, stale, or failed evidence makes the bootstrap capability absent and Hub
fail-closed rejects target assignment. The Hub consumes only the bounded
capability result and remains unaware of OS, container, deployment, or
platform-business details.

An affirmative object is permitted only when all of the following have passed
for the same exact runtime image and version, and their live evidence remains
valid for this bootstrap connection: (1) the T4B process-tree ownership suite;
(2) the T42F child-confidentiality boundary, including Provider denial of
Adapter credentials through ptrace, `/proc`, `process_vm_*`, and `pidfd_getfd`;
(3) the T42H explicit Provider environment allowlist and closure of every
credential-bearing descriptor; and (4) the T4C Provider-inaccessible
diagnostics boundary. A Provider is not presumed incapable before those gates
are proven. Until all four are valid, the Adapter MUST omit `capabilities` and
remain single-Session; it MUST NOT send `false` as a downgrade marker.

The selected Linux mechanism is `PR_SET_CHILD_SUBREAPER` plus pidfd-backed
descendant inventory. Before Provider spawn, GroupSupervisor fsyncs a protected
non-secret ownership/quarantine record outside Provider-writable storage. It
binds only opaque Worker/attachment identity, active generation/epoch, PID
start-time identity, state, and a bounded cleanup deadline; it contains no
credential, command, user content, path, or provider object. PID alone,
process-group membership, a parent exit, `setsid`, double-fork, or a Provider
acknowledgement never releases a writer lease.

The deployment supplies the fixed entry an Adapter-only durable ownership
store before any Provider spawn. Its root is writable only by the trusted
fixed entry, survives fixed-entry and container restart, is unavailable to a
Provider UID and its mount/descriptor namespace, and is not an EventStore,
workspace, home, tmpfs, log, or Provider-controlled path. A sealed manifest
contains a schema version, opaque runtime-instance identity, monotonic manifest
version, and the canonical ordered record-ID/digest set. Each record and each
manifest transition is written atomically, file-fsynced, then directory-fsynced;
the record is durable before the manifest may reference it. On every start the
fixed entry takes exclusive ownership of the root, enumerates it, validates the
manifest and every digest, and reconstructs or retains quarantine before any
Provider spawn. A missing root/manifest/record, an unexpected entry, a digest
or version mismatch, a failed fsync, or inability to exclude Provider access is
an integrity failure: it preserves/enters quarantine and denies multi-Worker.
No runtime or cleanup path may treat absence as proof that a prior tree exited.

On stop, GroupSupervisor attempts graceful provider-neutral termination, then
uses every known pidfd for bounded TERM, wait, KILL, and a fresh descendant
inventory. It releases a writer lease only after full-tree quiescence is proven.
Any pidfd/subreaper/inventory failure, timeout, unknown descendant, record
inconsistency, fork-storm bound failure, or restart uncertainty preserves
quarantine and denies every replacement writer. A container/PID1 exit must end
the full tree; on restart the Group verifies each protected record before any
Provider spawn. A runtime that exposes writable delegated cgroup controls,
permits cgroup tamper/self-move, or cannot prove these conditions remains
single-Session. This gate introduces no frame, EventStore record, or Hub-owned
process identity.

## Session Settings Capability Contract

This is a v2-only, provider-neutral contract for discovering and changing the
effective model and permission policy of one Session. It is an Adapter boundary:
the Hub validates, persists, and routes the bounded grammar but neither selects
a model nor translates a Provider operation. A deployment can associate a
Session with a Run outside this protocol; Task and Run identifiers never appear
in a Hub frame.

Only a v2 `hello.ack` that contains the exact `capabilities.settings` object
shown above permits settings frames. Its values are protocol limits, not an
Adapter claim that a particular control is mutable. A v1 acknowledgement omits
the object. An Adapter that cannot prove a Provider operation and a subsequent
read-back of the effective state MUST advertise the affected control as
read-only rather than inventing a fallback or Provider-specific command.

The Adapter publishes the current capability and confirmed effective values as
a durable `session.settings.capabilities` event. It republishes that event when
the available choices, mutability, reason, or confirmed effective value changes.
The Hub appends it through its ordinary authoritative EventStore path before
fanout. The exact payload is:

```json
{
  "schema_version": 1,
  "fingerprint": "sha256:a77186c8bf756736dc64be46864c21e4b10fd8ad8d719abf2e00dfa51c341000",
  "models": [
    { "id": "balanced", "label": "Balanced" },
    { "id": "reasoning", "label": "Reasoning" }
  ],
  "permission_modes": [
    { "id": "ask", "label": "Ask first" },
    { "id": "workspace", "label": "Workspace" }
  ],
  "effective_model_id": "balanced",
  "effective_permission_mode_id": "ask",
  "model_change": "allowed",
  "permission_change": "allowed",
  "model_read_only_reason": null,
  "permission_read_only_reason": null
}
```

All decoded objects in this section are exact: unknown or duplicate members are
rejected before a lossy map conversion, and omitted members are not defaulted.
The payload has exactly the ten members shown. `schema_version` is the JSON
integer `1`; `fingerprint` is `sha256:` followed by 64 lowercase hexadecimal
characters. `models` contains 1 through 32 entries and `permission_modes`
contains 1 through 16 entries. Every entry has exactly `id` and `label`.

An `id` is 1 through 128 ASCII bytes matching
`[A-Za-z0-9][A-Za-z0-9._:/-]{0,127}`; it is an opaque, provider-neutral
selection identifier rather than a Provider model name or protocol object. A
`label` is a valid NFC-normalized UTF-8 string of 1 through 128 bytes with no
Unicode control character. Each list is strictly sorted by the byte order of
`id` and contains no repeated ID. Both effective IDs must occur in their
respective lists. `model_change` and `permission_change` are each exactly
`allowed` or `read_only`. An `allowed` control has at least two choices and its
corresponding read-only reason is `null`; a `read_only` control has a reason
code matching `[a-z][a-z0-9_]{0,63}`. A provider with no model choice therefore
publishes one confirmed model with `model_change=read_only`; immutable
permission policy follows the same pattern. No payload may contain Provider
types, ACP objects, credentials, Session content, file paths, or permission
request data.

The capability fingerprint binds all semantics above. Its digest input is the
following versioned, length-delimited byte sequence, where `u8` and `u16be` are
unsigned integers and `utf8(s)` is the exact normalized UTF-8 byte sequence:

```text
utf8("agentwharf.settings-capability.v1") || 0x00 || u8(1) ||
u8(model_count) || each model in list order: u16be(len(id)) || utf8(id) || u16be(len(label)) || utf8(label) ||
u8(permission_mode_count) || each permission mode in list order: u16be(len(id)) || utf8(id) || u16be(len(label)) || utf8(label) ||
u16be(len(effective_model_id)) || utf8(effective_model_id) ||
u16be(len(effective_permission_mode_id)) || utf8(effective_permission_mode_id) ||
u8(model_change == "allowed" ? 1 : 0) ||
u8(permission_change == "allowed" ? 1 : 0) ||
u16be(len(model_read_only_reason_or_empty)) || utf8(model_read_only_reason_or_empty) ||
u16be(len(permission_read_only_reason_or_empty)) || utf8(permission_read_only_reason_or_empty)
```

`fingerprint` is the lowercase hexadecimal SHA-256 digest of those bytes with
the `sha256:` prefix. Any encoding that is not exactly this sequence, including
different ordering, normalization, duplicate members, missing null, an unknown
field, or an equivalent-looking JSON representation, is non-canonical and is
rejected.

A controlling Client requests one or both changes with the exact payload below:

```json
{
  "frame": "command",
  "cmd_id": "cmd_01H91",
  "type": "session.settings.change",
  "session_id": "ses_01H8X",
  "payload": {
    "capability_fingerprint": "sha256:a77186c8bf756736dc64be46864c21e4b10fd8ad8d719abf2e00dfa51c341000",
    "model_id": "reasoning"
  }
}
```

The payload has exactly `capability_fingerprint` and at least one of `model_id`
or `permission_mode_id`; those optional IDs use the same grammar as capability
entries. The Client must hold the literal `session:<id>:control` scope for the
target Session. `api:*`, group, view, attention, adapter, wildcard, and any
broader scope MUST be rejected for this command even when an Auth implementation
would otherwise authorize ordinary Session control. The Hub applies the 64 KiB
frame limit before decode, validates the canonical grammar and live Session
binding, and resolves the supplied fingerprint against the last persisted
capability for that exact Session before routing.

Every settings request first enters a durable, atomic `SettingsCommandReserve`
EventStore transaction. It conditionally verifies the current persisted
capability fingerprint, rejects a stale or mismatched request,
and records `{session_id, cmd_id, request_fingerprint, requested_model_id?,
requested_permission_mode_id?, reservation_version, delivery_deadline,
operation_deadline=null,
writer_connection_epoch, writer_credential_generation, writer_lease_id,
status=delivery_pending}`. The persisted writer tuple is the current live
Adapter connection epoch, active credential generation, and Hub-issued opaque
writer lease ID; it contains no Provider identity or credential. The tuple
is Hub/Adapter routing metadata only and is never added to a public settings
capability or effective-event payload. The tuple
`(session_id, cmd_id)` is unique; an identical retry
returns `command.ack(status=duplicate)` without routing again, while a different
payload for that tuple is rejected as `cmd_id_reused`. The same transaction
enforces at most one nonterminal reservation per Session. It never queues a
second one: it returns `command.ack(status=rejected,
reason=settings_change_pending)`. `delivery_deadline` is the original Store
clock plus exactly five seconds; it bounds only the Hub-to-Adapter routing
receipt. The reservation contains only the bounded opaque IDs
from this section and no Provider object, credential, content, path, or
permission-request detail. A pre-route fingerprint mismatch returns
`command.ack(status=rejected, reason=stale_capability)` and creates neither a
reservation nor a durable effective event; the durable `stale_capability`
outcome below is reserved for a race after routing.

After reservation, the Hub sends the request only to an Adapter holding the
live writer lease matching the stored writer tuple. It derives and rechecks that
tuple from the authenticated live Adapter connection context; the Adapter's
ordinary hop-by-hop `command.ack(accepted)` carries no added JSON members. The
receipt confirms delivery only; the Adapter MUST NOT begin its Provider operation
yet; it starts a local monotonic 30-second operation fence immediately before it
writes that receipt. Only after receiving it does the Hub CAS the reservation
from `delivery_pending` to `pending`, atomically set `operation_deadline` to its
current Store clock plus exactly 30 seconds, and send the following Adapter-only
v2 control frame on that same current WebSocket:

```json
{
  "frame": "settings.delivery.execute",
  "session_id": "ses_01H8X",
  "cmd_id": "cmd_01H91",
  "reservation_version": 7,
  "operation_timeout_ms": 30000
}
```

This exact frame is Hub -> Adapter only: it is never sent to a Client, persisted
as an event, replayed, logged as a delivery control, or accepted on v1. It is limited
by the ordinary 64 KiB frame bound. It has exactly the five members shown:
`reservation_version` is a positive 64-bit integer and `operation_timeout_ms`
is exactly `30000`. Unknown, duplicate, missing, or mismatched members are
rejected. The Hub emits the frame only after its CAS and only while the same
persisted writer tuple remains live; the tuple is bound from the authenticated
connection context rather than copied into the frame.

The Adapter may begin only after receiving this frame, verifying it against its
authenticated connection context and reservation, and confirming that its local
monotonic fence has not expired. It uses that local 30-second fence, not a
separate wall clock, and must not apply or report success after expiry. Because
the local fence starts before the Hub receives the delivery receipt, it expires
no later than the Hub's Store-clock `operation_deadline`. The Hub returns
`command.ack(status=accepted)` to the Client after the same transition; that
status means bounded delivery confirmation, never Provider success. If
delivery fails or reaches `delivery_deadline` before that receipt, the Hub conditionally finalizes the
`delivery_pending` reservation as `rejected` with `adapter_delivery_failed` and returns a
rejected client acknowledgement. If a send or acknowledgement is ambiguous, the
Hub never reroutes it; recovery uses the fenced ledger rules below. A lost client
acknowledgement remains a normal `cmd_id` duplicate on retry and the durable
terminal event is the outcome source.

The Adapter must reject a stale fingerprint, an unavailable ID, or a read-only
control without selecting a default. It performs at most one provider operation
at a time and has a 30-second provider response deadline. A mutable control is
allowed only when the Adapter can prevent an operation from applying after that
deadline and can read back the Provider's actual effective values. Otherwise it
is read-only. This keeps the pending state bounded without a hidden retry,
queue, or silent fallback.

Every durable reservation has exactly one durable
`session.settings.effective` terminal event. Its exact payload is:

```json
{
  "cmd_id": "cmd_01H91",
  "request_fingerprint": "sha256:a77186c8bf756736dc64be46864c21e4b10fd8ad8d719abf2e00dfa51c341000",
  "effective_fingerprint": "sha256:a77186c8bf756736dc64be46864c21e4b10fd8ad8d719abf2e00dfa51c341000",
  "outcome": "applied",
  "effective_model_id": "reasoning",
  "effective_permission_mode_id": "ask",
  "reason_code": null
}
```

The payload has exactly the seven members shown. `outcome` is one of `applied`,
`rejected`, `timeout`, `unsupported`, `stale_capability`, `outcome_unknown`, or
`mismatched_effective`; a non-`applied`
outcome has a required reason code matching `[a-z][a-z0-9_]{0,63}`, while
`applied` has `reason_code` `null`. The effective fingerprint and IDs must refer to a published capability
event for the same Session that the Hub has already persisted. Before append,
the Hub resolves that reference against its durable capability state and rejects
an unresolvable fingerprint or ID without creating an effective event. `applied`
is emitted only after execution-side acceptance and read-back.
`rejected`, `timeout`, `unsupported`, and `stale_capability` preserve the
effective values of the reserved capability; `stale_capability` first causes the
Adapter to publish the current capability. `outcome_unknown` is non-success but
uses the reconnecting Adapter's newly persisted read-back capability rather than
claiming that the reservation's old values remain current.
`mismatched_effective` is likewise non-success but references the Adapter's
newly persisted actual read-back capability. The Client keeps that actual value
as authoritative, retains the draft, and displays the bounded mismatch reason;
it MUST NOT present the Provider's differing value as a successful fallback or
restore an obsolete reserved value.

Only a conditional `SettingsCommandFinalize` transaction can end a reservation.
It checks the exact `(session_id, cmd_id, reservation_version)` and expected
nonterminal state (`pending` for a delivered Adapter result, `delivery_pending`
for failed delivery or `delivery_deadline`, or `recovery_pending` for recovery), appends the
one terminal event, marks the reservation terminal, and releases the
per-Session pending slot in the same EventStore transaction. An Adapter result
and `operation_deadline` race through that same compare-and-swap; the loser is
dropped. On `operation_deadline` the Hub finalizes `timeout` with the last
confirmed capability, never `applied`; the Adapter must not apply or report
success after that deadline. A timeout, adapter disconnect, or Hub restart is
not an implicit Provider success and cannot cause rerouting.

A normal Adapter finalization is bound by the Hub to the submitting authenticated
connection's writer tuple; the Hub MUST CAS that derived tuple against the
persisted and current live writer tuple in the same transaction. The tuple is
not a public effective-event member. A stale, replaced, revoked, expired, or old-epoch Adapter cannot
acknowledge delivery, publish a result, or finalize this reservation. On writer
lease loss or replacement the Hub atomically changes a nonterminal reservation
to `recovery_pending`, fences normal finalization, and discards every result
from the old tuple. The new writer may not adopt the old operation: after it
publishes fresh read-back capability, only the recovery path below may terminally
write `outcome_unknown`. This tuple fence remains in durable EventStore state
across Hub restart and closes the old-connection result race.

Finalize also binds an Adapter proposal to its reservation: `request_fingerprint`
must equal the reserved request fingerprint. For `applied`, every requested
model or permission ID must equal the matching effective ID in the referenced
current capability, and every unrequested control must equal the effective value
of the reserved capability. A mismatch, including a Provider defaulting a
requested value or coupling an unrequested control change, MUST NOT append
`applied`. The Adapter first publishes its actual read-back capability; the Hub
then finalizes `mismatched_effective` against that actual capability with reason
`provider_mismatched_effective`, without inventing a fallback or rewriting the
request. This rule makes each provider-visible deviation explicit to replaying
Clients.

The reservation and terminal ledger are durable EventStore state, not a process
map. On restart the Hub reconstructs every pending reservation, fences new
settings commands for that Session, and never redelivers the old request. A
reconnecting Adapter first publishes a fresh read-back capability and then may
finalize the original reservation with an execution-side result. If it cannot
prove the original result, the Hub finalizes exactly once with
`outcome_unknown` and reason `recovery_unconfirmed`; the Adapter publishes both
controls as `read_only` with the same reason. The Hub accepts a new settings
change only after that capability refresh and terminal finalize commit. This
recovery rule prevents a restart from converting a missing acknowledgement into
a duplicate or conflicting Provider operation.

## Run Control Completion Contract

This is a v2-only contract for the existing `session.interrupt` and
`session.stop` commands. `session.interrupt` requests cancellation of the
current Provider turn while the Session remains usable. `session.stop` requests
a terminal end of the current Session; it never stops a VM, deletes a Task/Run,
or represents Console disconnect. A v2 `hello.ack` must include the exact
`capabilities.run_control` object above before the contract is available.

The Adapter publishes durable `session.run.capabilities` whenever either control
changes. Its exact payload is `{ "schema_version": 1,
"interrupt_supported": true, "stop_supported": true }`; it has exactly those
three members, booleans are literal, and no Provider API/object/credential is
included. The Hub applies its 64 KiB bound before decoding and rejects unknown,
duplicate, or non-canonical members. `capability_version` is the Store-assigned
sequence of this accepted durable event; it is Hub ledger metadata, never a
payload member or Client-supplied value. A capability is current only when its
persisted writer tuple equals the live authenticated Adapter tuple
`(connection_epoch, active_credential_generation, writer_lease_id)`. A newly
connected, replaced, revoked, or recovered writer must publish a fresh capability
before any control is eligible. An absent, stale, or tuple-mismatched capability
fails closed with `command.ack(status=rejected, reason=run_control_unavailable)`
and creates no reservation, Provider operation, state event, or outcome event.

A Client may send an existing command only with exact `session:<id>:control`;
`api:*`, group, view, attention, adapter, and wildcard scopes are rejected. The
Hub rejects a current false capability before routing with
`command.ack(status=rejected, reason=interrupt_unsupported)` or
`stop_unsupported` and creates no reservation, Provider operation, state event,
or outcome event.

For a supported control, `command.ack(status=accepted)` proves only Hub routing.
`RunControlReserve` atomically verifies the current durable capability and its
current writer tuple, the current Session state projection, and the exact
operation. It records `{session_id, cmd_id, operation, capability_version,
reservation_version, pre_control_state, pre_control_state_seq,
writer_connection_epoch, writer_credential_generation, writer_lease_id,
deadline, status=pending}`. `interrupt` is eligible only from `busy`; `stop` is
eligible only from `starting`, `ready`, `busy`, `waiting_permission`, or
`recovering`. `ended`, `error`, and every other state reject before routing with
`run_control_invalid_state`. The reservation contains only bounded opaque IDs
and enum values, never Provider data, credential, content, path, or permission
details. A same-operation retry of an existing `cmd_id` returns `duplicate`
without redelivery; a different operation for that `(session_id, cmd_id)` is
`cmd_id_reused`. The transaction permits one nonterminal control per Session,
sets an exact 30-second Store-clock completion deadline, and rejects another
request as `run_control_pending`. The Hub routes only to the matching live writer
tuple. It never auto-retries an interrupt or stop after adapter loss, Hub
restart, or deadline. It atomically finalizes each reservation once with a
durable `session.run.outcome` event:

```json
{
  "cmd_id": "cmd_01H91",
  "operation": "interrupt",
  "outcome": "completed",
  "completion_state": "ready",
  "reason_code": null
}
```

The payload has exactly five members. `operation` is `interrupt` or `stop`;
`outcome` is `completed`, `rejected`, `timeout`, `unsupported`, or
`outcome_unknown`; non-completed outcomes require reason code
`[a-z][a-z0-9_]{0,63}`, while completed has `reason_code=null`.
`completion_state` is `ready` only for a completed interrupt and `ended` only
for a completed stop; it is null otherwise.

Only `RunControlFinalize` can terminate a reservation. A successful Adapter
proposal is bound to its `cmd_id`, `reservation_version`, and authenticated
current writer tuple; those bindings are Hub/Store metadata, not public
`session.state` members. In one conditional EventStore transaction the Hub CASes
the exact reservation version, capability version, pre-control state sequence,
and current writer tuple. For a completed interrupt it appends a current-writer
`session.state busy -> ready` whose Store sequence is greater than
`pre_control_state_seq`, then appends the outcome with a greater sequence. For a
completed stop it similarly appends `nonterminal -> ended(reason=user_stop)`,
then the outcome. A pre-existing, unrelated, stale-writer, or unbound
`session.state` never finalizes a reservation. Replaying Clients treat that
ordered state transition as authoritative completion proof, not the command ack.

Provider rejection finalizes `rejected/provider_rejected`; the deadline finalizes
`timeout/run_control_timeout`; a lost, replaced, revoked, expired, or old-epoch
writer atomically fences normal finalization, marks its capability unavailable,
and finalizes `outcome_unknown/adapter_disconnected`. Hub restart reconstructs
the durable reservation and finalizes it once as
`outcome_unknown/recovery_unconfirmed` before admitting a new control. No new
writer may adopt an old operation. It must publish a fresh current-tuple
capability after recovery, and only then can a later control reserve. Console
disconnect/browser close sends no run-control command and creates no control
outcome. A pending permission request is never approved, denied, expired, or
otherwise changed by either control.

An Adapter must not auto-approve, deny, expire, or otherwise mutate an already
pending `permission.request` while changing policy. Existing permission
requests and decisions retain their original durable facts. A newly applied
policy affects only permission requests first created after the durable settings
outcome. Reconnect replay includes both capability and outcome events, so a
Client displays only Adapter-confirmed values; a local draft may be retained but
is never shown as effective. On rejection or timeout the Client restores the
last confirmed value, retains the draft, and displays the bounded reason code.

## Ephemeral `x.vm.idle_warning`

v2 emits only the opaque platform extension:

```json
{
  "vm_id": "vm_01H8X...",
  "seconds_until_suspend": 600,
  "suspend_at": "2026-06-21T12:30:00Z",
  "message": "This VM will pause soon because it has been idle."
}
```

- `seconds_until_suspend` is non-negative at send time; `suspend_at` is RFC3339 UTC.
- The event omits `seq` and MUST NOT enter EventStore, replay, durable browser
  state, or durable analytics.
- The Hub receives a bounded injected version-to-opaque-type map. It selects by
  negotiated version only and MUST NOT hardcode the type, inspect `vm_id`, or
  infer VM lifecycle semantics.
- Durable `vm.idle_10m` notification/outbox delivery is unchanged and outside
  this protocol event stream.

## Legacy Window And Sunset

v1 `session.idle_warning` is supported through `2027-01-08T00:00:00Z`, 180
days after v2 spec approval. Before that timestamp v1 emits only the legacy
name and v2 emits only `x.vm.idle_warning`. T1B is the separate docs-only
removal contract. T15K and T52B remain time-gated until T69 and approved T1B.
